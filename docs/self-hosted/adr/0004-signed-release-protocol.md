# ADR-0004 — Verified artifacts with freshness and compatibility policy

Status: PROPOSED; exact trust-root/metadata protocol and operator procedure require security approval.

Context: current SSH pipeline transfers SHA-tagged Docker archives with matching revision labels. Labels/tags are not cryptographic signer identity. Private-master goal conflicts with current public repository and needs a separate governance decision.

Proposal: build immutable OCI digest artifacts in dedicated release CI; publish SBOM, provenance and Cosign signatures with explicit allowed issuer/subject or reviewed offline key policy. A signed, versioned metadata envelope references app digest, migration artifact digest, schema target/min/max, agent/protocol/compose versions, expiry, rollout channel/ring and minimum accepted security version. Prefer an established TUF-compatible client/library for root/targets/snapshot/timestamp rather than bespoke crypto or treating an expiring signed JSON file as a complete anti-freeze system. Equivalent protocols require explicit security review, not an undocumented fallback.

Bootstrap verifier/root must come from a pinned independently reviewable release path with rotation/recovery documented. Verify SHA and authorized signature before any execution/import; never fetch a checksum from the same untrusted source and call it authentication. No working curl-pipe installer until this chain exists. Seller registry pull credentials must be scoped/short-lived; this capability is a requirement, not a verified GHCR feature. GHCR is pending feasibility: documented PAT classic / CI GITHUB_TOKEN flows do not by themselves provide per-install expiring grants. Choose a supported delegated distribution mechanism before installer delivery; never embed or distribute operator PAT, CI GITHUB_TOKEN or source repository access to sellers. See ../visibility-impact.md.

Signature enforcement for initial bootstrap, image and install manifest belongs to P0 before A03/A20; PR-07 P1 adds fleet update orchestration, not the first trust check. Private source versus public bootstrap verifier/trust-root distribution policy must be reviewed explicitly; seller receipt of runtime images does not grant source access or prove source confidentiality.

Updates default notify-only for pilot, then explicit opt-in windows. Separate code approval, artifact publication and rollout approval; local helper remains final gate. Reject stale metadata, bad signer, tampered artifact, unsupported compatibility and replayed/downgrade release. Clock failure pauses updates, not commerce. Persist local highest-trusted metadata/version with explicit authorized recovery override procedure, not remote force flag.

Validation: U01–U08,U10,U15–U17, offline/freeze/key-compromise drills. Signing key revocation/rotation, registry cost/retention and trustworthy first installation remain open. Existing production autodeploy is excluded from this new pipeline until separately reviewed.

## Private distribution and bootstrap decision review

Official [GHCR authentication](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry) describes PAT classic and Actions GITHUB_TOKEN contexts; this does not prove installation-scoped expiring seller grants. CI credentials must never be passed to seller hosts.

Recommend evaluating [Harbor project robots](https://goharbor.io/docs/2.15.0/working-with-projects/project-configuration/create-robot-accounts/) with one expiring pull-only robot per installation. A separate broker authorizes the bound device, checks entitlement, provisions/renews credentials and records non-secret audit metadata. Robots are bearer secrets and project-scoped, not necessarily digest-scoped. Separate artifact projects if entitlement isolation requires it. Use protected local auth storage, TLS and redacted logs. Test disabling a robot plus any already-issued registry token lifetime; state the observed revocation bound rather than promising instant denial. Registry failure leaves current commerce running.

A custom OCI token gateway could narrow repository/action grants but adds security-service ownership, blob-redirect/cache exposure and key lifecycle. Prefer supported registry operation first. Both remain unprovisioned alternatives. Owner must approve cost/bandwidth/quota/backup/on-call requirements; disposable tests must prove cold pull, expiry, renewal, cross-install isolation and revocation. If none meets requirements, private delivery remains BLOCKED. No shared permanent PAT fallback.

Bootstrap trust: distribute a minimal verifier/root through an independently reviewed channel, pin version/hash/root in audited instructions, and authenticate the verifier itself through a pretrusted OS/package or release verification mechanism. A root first downloaded from the same compromised portal is not independent trust. Select this initial channel before enabling any working one-line installer. Verify platform, SHA and authorized signer before executing the installer. Use established TUF metadata validation/root rotation and expiry before selecting targets. References: [Cosign](https://docs.sigstore.dev/cosign/verifying/verify/), [TUF](https://theupdateframework.github.io/specification/).

Name signer issuer/subject, root custodians, recovery threshold and two-person broad-rollout approvers. Test wrong signer, revoked fresh install, stale clock, truncated download, root rotation and compromised-key recovery. No source visibility, executable bootstrap or release pipeline is changed here.
