# Disposable recovery snapshot harness

M1-04 implementation component, not a seller backup service or a claim of runtime validation. Requires Node 22+. Uses Node's AES-256-GCM authenticated encryption with a random nonce, a caller-provided random 32-byte key file, exclusive writes and SHA-256 verification of every restored file. No dependencies, credentials, database connections or Docker commands are embedded.

The scope is deliberately bounded to synthetic fixtures (64 MiB plaintext, 4,096 files). Production streaming backups, retention, off-VPS storage, RPO/RTO and recovery-key custody remain release gates. Same-host encryption testing is not off-server durability proof. Local Windows runs do not establish Ubuntu or VPS restart support.

## Input contract for the disposable Linux runner

1. Create a private temporary directory on an authorized disposable host. Set `umask 077` and generate a random 32-byte binary key outside the source fixture and backup artifact. Preserve the key separately; never upload it with CI artifacts.
2. Run `node deploy/self-hosted/recovery/fixture-snapshot.mjs init <new-source-dir>`. Existing roots are rejected. This creates a fresh disposable sentinel and empty `media/` and `recovery/` directories.
3. Seed synthetic orders/media into the isolated source store. Stop app writes before capturing data. Export a plain SQL PostgreSQL dump into `<source>/database.sql` using `pg_dump --no-owner --no-acl`; copy durable media into `media/` and installation-only synthetic recovery configuration into `recovery/`. Database and media consistency depends on this quiescence barrier; the snapshot tool cannot infer it. Never point these steps at production.
4. Run `node deploy/self-hosted/recovery/fixture-snapshot.mjs backup <source> <separate-archive-dir>/snapshot.enc <key-file>`. The archive parent must exist, be separate from the source and contain no symlink components. Existing archives are never overwritten.
5. Run `node deploy/self-hosted/recovery/fixture-snapshot.mjs restore <archive> <new-target-dir> <key-file>`. Authentication, path and checksum validation occur before target creation. A fresh target fixture identity is generated; an existing target is rejected. A failed filesystem write leaves a partial disposable target for diagnosis, never an automatic delete/retry against an existing path.
6. Import restored `database.sql` into a **different new fixture DB/Compose project**, copy restored media and recovery files to its private volumes, and start the independent restored store. Compare exact synthetic order records, media checksums and critical auth/navigation behavior. `verify <fixture>` emits names/hashes only, no file contents or secrets.
7. Record safe JSON command summaries, exact image digests, source/restore fixture IDs, free disk/inodes, peak RAM/disk, startup/restore duration and runtime test outcomes. Never artifact the dump, recovery config, key or populated secret files. Retain only the encrypted archive if policy permits, separately from its key.

The tool refuses unknown top-level source files, symlinks, special files, invalid relative archive names, overlapping output/source paths, keys inside the snapshot, oversized inputs, malformed ciphertext, wrong keys and all overwrite attempts. It does not remove any resource. Only a fixture-owner-checked caller may clean up its own temporary test resources.

## Docker fixture integration

After `tests/runtime.sh` has seeded `fixture_persistence` and the persistent media sentinel, call `bash "$repo/deploy/self-hosted/recovery/test-stack.sh" "$fixture_root/stack"` from that runner. The harness accepts only `/tmp/jetseller-runtime.*/stack` with a matching synthetic marker/project/database/domain and Compose ownership labels. It stops the source app before capturing a PostgreSQL dump, media and private recovery configuration. It verifies the authenticated encrypted snapshot in a separate directory and imports SQL into a newly created pinned PostgreSQL container with its own volume, password, no published port and no network. It checks the exact synthetic row and every media/config checksum. Cleanup only stops its own labeled destination; the source and destination data remain until the disposable runner is destroyed.

This requires the M1-02 `images.lock.json` and fixture layout; this branch does not duplicate packaging. CI should run the Node tests before the Docker script. Never upload its private temporary workspace or key. JSON summaries contain counts, hashes, fixture IDs and durations only. The harness does not restart a VPS or prove off-host backup durability, application upgrade recovery, restored-browser navigation or a real public ACME certificate. Those remain observed release gates.

Run unit negatives with `node --test deploy/self-hosted/recovery/fixture-snapshot.test.mjs`. An Ubuntu 24.04 runner must execute the Unix permission and symlink cases; Windows skips the Unix symlink case explicitly. Container persistence, host reboot, real PostgreSQL import, browser regressions, center-offline behavior, signing and live domain HTTPS must be separately observed before claiming M1-04 or pilot completion.
