# Deployment and rollback runbook — approval required

This task stops at review. Do not merge, run a production migration, or deploy from this branch without the user's separate approval. Do not use destructive reset/db-push commands. No production commands below were executed during implementation.

## Reviewed database-first transition

1. Review the migration, CI, capacity, deployment lock, health checks and application artifact. Retain the current compatible artifact/image and record its immutable identifier. The release instruction received on 2026-10-30 requires a restricted custom-format PostgreSQL backup before any Production database change: verify successful `pg_dump -Fc`, nonempty file and successful `pg_restore --list`. Stop on backup failure. A previously failed Helipod snapshot is not recovery evidence. Prefer a separately secured copy when available; never log credentials or commit the backup.
2. Apply the official additive Prisma migration during an approved release. It sets a 3-second lock timeout and 30-second statement timeout and archives original legacy settings without modifying Product rows. On lock timeout it rolls back as a unit. Investigate the failed migration and use the established Prisma resolve/retry procedure; do not bypass the database safety guard.
3. From the new migration/build-stage artifact (which retains tsx), run `node --conditions=react-server --import tsx scripts/promotions/legacy-cutover.ts` with approved production environment injection. Default mode only inventories archived/current legacy records; never print environment variables or connection strings. Inventory currently stops if it exceeds 1000 records, requiring an explicit reviewed batching improvement before a larger cutover.
4. If inventory is empty, no conversion is needed. Otherwise freeze legacy promotion edits and product pricing changes for the maintenance window. Review each original schedule, manual price, effective regular price and SKU price. Distinct legacy intervals MUST NOT be merged automatically. Overlapping intervals cannot both become central campaigns: an authorized business decision must choose new explicit schedules, participants, prices or retirement. Do not silently discard a promotion.
5. Prepare a restricted local JSON mapping with `actorId`, `campaigns` and optional `retire`. Actor must be an active authorized admin from the database. Each campaign uses the validated campaign DTO (`id:null`, `expectedVersion:0`, name, `status:"SCHEDULED"`, absolute UTC startsAt/endsAt, `resolveLegacy:true`, items). Each retired record supplies productId and expectedUpdatedAt. Review this file before applying. Use the CLI's current usage/validation errors for exact invocation; the only write mode is `apply <file>` with `GHEVERHAN_FLASH_CUTOVER_APPROVED=CONVERT_LEGACY_FLASH_SALE`.
6. Each campaign/retirement is atomic, but the whole mapping file is NOT one transaction. Keep traffic/legacy writers paused during conversion, record completed campaign IDs, and recover forward from the first failed item. Services reject stale original snapshots, invalid prices and overlapping schedules. A legacy row edited after the archive was captured fails closed and requires a separately reviewed reconciliation; never overwrite its archive automatically.
7. Conversion links the retained archive to its campaign and clears only the resolved legacy flash controls. Historical manual Flash Sale used `salePrice` as its promo price; by default retiring/converting that manual mechanism clears that overwritten price. An explicitly reviewed retirement can supply `retainManualPriceAsRegular: true` to retain the CURRENT archived manual sale price as a regular discount atomically with retirement. This requires both Marketing update and product update permissions, an unchanged archived snapshot, matching product timestamp, manual legacy flag and a positive sale price below base price. The mapping cannot set an arbitrary new price. Audit records capture the prior and resulting regular price in the same transaction. Scheduled legacy records retain their genuine regular sale price without this option. Retired expired schedules remain archived rather than being turned into fake future campaigns.
8. Run the existing appearance/storage/schema preflight from the new artifact. Campaign preflight requires the exclusion constraint, control row and zero raw legacy flags/price/dates. A failed gate blocks application traffic switch. Verify expected campaigns, participants, timestamps and master regular prices, then switch to the approved artifact using the existing deployment lock.
9. Verify health endpoints, Home/Flash listing clocks, catalog/PDP, variant quick-add, cart, Buy Now and checkout quote before allowing customer traffic. Verify at least one boundary and Marketing edit/end invalidation in the approved environment. Do not place a real order or modify customer data as a diagnostic.

## Application rollback and database limitations

- Prefer a forward fix or rollback to a campaign-compatible artifact with the same additive schema. Keep the new schema and archive; do not drop tables or reverse history.
- The old V4 application does not understand central campaigns. After legacy conversion it will not apply central promotional prices, and its old Marketing controls can recreate the two-source problem. Therefore blindly switching to the old image is NOT a transparent promotional rollback. If only that image is available, keep traffic/Marketing paused and obtain a business decision about ending promotions or a reviewed compatibility artifact before resuming.
- If no legacy conversion or central campaign has occurred, the additive schema itself preserves old Product data. Still assess any writes since release before switching versions.
- Original legacy values remain archived, but automatic restoration is intentionally absent: it could overwrite later legitimate product edits or reactivate expired/overlapping promotions. Any restoration needs a separately reviewed, version-aware operation.
- Without a database recovery copy, an application image rollback cannot undo data changes, restore lost records or guarantee database point-in-time recovery. This change avoids destructive DDL and never claims that image rollback provides those capabilities.

## Post-cutover checks

Confirm zero unresolved raw legacy settings; all campaign windows valid/nonoverlapping; unique participants; no active incompatible prices; audit events present; master prices preserved except explicitly reviewed manual legacy retirement; healthy PostgreSQL/application; adequate free disk; no errors/hydration mismatch; no stale checkout quote acceptance. Keep the archive and rollback artifact. Do not prune persistent media, database volumes or rollback images as part of this feature.
